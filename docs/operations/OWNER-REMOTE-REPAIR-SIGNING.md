# Firma offline de una reparación supervisada

El firmador `scripts/sign-supervised-github-repair.cjs` crea únicamente una firma Ed25519; no consulta GitHub, aplica un parche ni autoriza rollback o merge. Debe ejecutarse en un equipo POSIX confiable del propietario, fuera de CI, con su reloj correcto y una clave privada Ed25519 ya existente. Windows queda rechazado: los bits POSIX de Node en Windows no demuestran privacidad de ACL. El root, los procesos con el UID efectivo del propietario y el sistema operativo forman parte del límite de confianza.

Usar el firmador, sus dependencias y el ejecutor desde el mismo SHA revisado y verificado, instalado fuera del control de código no confiable. El PR #274 modifica la canonización del orden de rutas: una firma antigua puede dejar de coincidir. No agregar bypass de compatibilidad; preparar y revisar un nuevo plan con grant y nonce nuevos bajo el SHA vigente.

Antes de firmar, el operador debe presentar para revisión el repositorio, PR draft existente, rama permitida, `main`, HEAD y árbol exactos, dos rutas Kotlin y sus diffs, hashes Git de bytes originales y candidatos, explicación, pruebas RED/GREEN independientes, Judge y el digest calculado con `digestBranchCandidate`. Una vista no firmada no concede autorización. El ejecutor todavía debe verificar GitHub, el oráculo JVM original aislado, Judge local y ledger antes de escribir.

El JSON de intención contiene exclusivamente `plan`, `files` y `ownerGrant`. Debe guardarse en la representación compacta exacta producida por `JSON.stringify`, sin salto de línea final, y ser ese mismo archivo el que se muestra para revisión. Así se rechazan claves duplicadas y representaciones ambiguas:

- `plan`: `repository`, `prNumber`, `branch`, `expectedHeadSha`, `expectedMainSha`, `expectedTreeSha`, `operation`.
- `files`: exactamente dos objetos con `path`, `before`, `after`, `beforeBlobSha` y `afterBlobSha`, sujetos a los límites del ejecutor. Los contenidos y los hashes deben corresponder exactamente a lo revisado.
- `ownerGrant`: `ownerLogin`, `ownerId`, `repo`, `prNumber`, `branch`, `headSha`, `baseSha`, `planDigest`, `nonce`, `expiresAt`, `operation`. `expiresAt` es tiempo Unix en milisegundos, futuro y a lo sumo 15 minutos. `planDigest` procede del código del ejecutor, no de texto aportado por el PR. El grant debe coincidir con el plan.

El nonce de reparación debe generarse con un generador criptográfico en el equipo confiable y ser nuevo; p. ej., 32 bytes aleatorios codificados como base64url. La novedad se verifica mediante el ledger persistente del ejecutor al aplicar; este firmador no consulta ese ledger y no garantiza por sí solo que un nonce no haya sido usado. El rollback requiere otro grant, dominio y nonce.

El pin independiente `ULTRA_SENTINEL_OWNER_SIGNING_PUBKEY_SHA256` es el SHA-256 hexadecimal minúsculo de la clave pública Ed25519 en formato DER SubjectPublicKeyInfo, establecida por el propietario fuera del JSON no confiable. Debe compararse mediante un canal independiente con la clave pública fijada en el operador. El firmador deriva la clave pública de la privada y rechaza un pin distinto; no crea claves.

Configure `ULTRA_SENTINEL_OWNER_SIGNING_KEY_FILE` con la ruta absoluta de la clave privada y ejecute el script con la ruta absoluta al JSON revisado. Ambos archivos deben ser regulares, de un enlace y propiedad del usuario; la clave no puede ser legible por grupo u otros y el JSON no puede ser modificable por ellos. Todos los directorios ancestros, incluida la raíz, deben pertenecer a root o al UID efectivo del operador y no pueden ser symlinks ni escribibles por grupo u otros. La lectura comprueba ancestros con `lstat` y usa `O_NOFOLLOW` para el archivo final; no emplea `openat2` ni abre la cadena de directorios de forma atómica. La protección depende de que root, el UID efectivo y el host sean confiables y no reemplacen los ancestros entre comprobación y apertura. Guarde la salida de firma únicamente en un archivo protegido, pues es una capacidad vinculada al grant; no la publique. El script no ejecuta el plan.

La firma corresponde exactamente a `Ultra-Sentinel:github-pr-branch-commit:v1\n` seguido de `stableOwnerBranchGrant(ownerGrant)`. Los campos desconocidos, el cambio de bytes/digest, alcance o pin, y las autorizaciones vencidas o demasiado largas bloquean la firma. La clave privada nunca se comparte con el ejecutor ni con GitHub.
